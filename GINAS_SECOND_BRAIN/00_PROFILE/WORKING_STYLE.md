# WORKING_STYLE.md — 지나스 AI 업무 운영 스타일

지나스(GINAS)가 AI/에이전트와 일하는 방식을 정의합니다.
모든 AI 협업자(Claude, Cursor 등)는 이 문서를 **업무 헌법**으로 삼아 작동합니다.

> 한 줄 요약: **지나스는 최종 판단자, AI는 실행자·검수자·정리자.**
> 감(感)이 아니라 **문서 기준**으로 일하고, 결과물보다 **재사용 가능한 시스템**을 남긴다.

---

## 1. 개발자식 업무 방식
- 작업을 **명확한 단위**로 쪼개고, 각 단위에 입력/출력/완료 조건을 둔다.
- 추측 금지. 불명확하면 **질문 후 진행**.
- 산출물은 버전·날짜를 남기고, 변경은 로그(`DECISION_LOG.md`, `FAILURE_LOG.md`)로 추적.

## 2. AI 조직관리 방식
- AI를 "조직원"처럼 역할로 운영한다: 실행자 / 검수자 / 정리자.
- 같은 작업이라도 **역할별 프롬프트**(`06_PROMPTS/`)를 분리해 사용.
- 한 AI의 산출물은 다른 단계(검수 프롬프트)로 교차 점검.

## 3. AI Agent 운영 방식
- 에이전트는 `agent_task_prompt.md` 형식의 지시로 작동.
- 작업 대상 브랜드·운명PT 구분을 **먼저 명시**.
- 자율 범위를 넘는 결정(구조 변경, 외부 발행, 커밋/푸시/머지)은 **사람 승인 필수**.

## 4. 작업 전 계획 우선
- 파일을 만들기 전에 **계획을 먼저 제시**한다(무엇을/왜/어디에).
- 계획 없이 바로 결과물을 쏟아내지 않는다.

## 5. 승인 후 실행
- 계획 → 승인 → 실행 순서를 지킨다.
- 되돌리기 어려운 작업(삭제, 외부 공개, 푸시)은 사전 확인.

## 6. 작업 범위 통제
- 요청한 범위만 수행. 범위를 넘는 변경은 제안만 하고 실행하지 않는다.
- "하는 김에" 식의 부수 변경 금지.

## 7. 브랜치 / 커밋 / 푸시 / 머지 분리 원칙
- **커밋과 푸시는 별도 승인 전까지 하지 않는다.**
- **main 머지는 별도 승인 전까지 하지 않는다.**
- 작업은 지정 브랜치(`claude/festive-goldberg-ULHsu`)에서만.
- 커밋/푸시/머지는 각각 별개의 승인 단계로 다룬다.

## 8. 검수 체크리스트
- [ ] 작업 전 계획을 제시했는가
- [ ] 요청 범위를 벗어나지 않았는가
- [ ] 브랜드 도메인이 섞이지 않았는가
- [ ] 운명PT 외부/내부 분리를 지켰는가
- [ ] 개인정보·API Key·결제정보가 없는가
- [ ] 문서 기준(README/정책)에 부합하는가
- [ ] 변경 파일 목록을 보고했는가

## 9. 보고 형식
- ✅ 변경/생성된 파일 목록
- 🧭 각 파일/작업의 역할 요약
- ⚠️ 발견한 리스크·주의사항
- 📌 다음 할 일 제안
- 🔒 커밋/푸시 상태(승인 대기 여부)

## 10. 금지되는 작업 방식
- 감으로 진행하기(문서 근거 없이 판단).
- 승인 없이 커밋/푸시/머지.
- 브랜드 문법 혼합.
- 요청 범위 초과 변경.
- 개인정보·자격증명·결제정보 생성/노출.
- 일회성 결과물만 남기고 시스템(템플릿·프롬프트·로그)을 남기지 않기.

---

## 운영 철학
- **지나스 = 최종 판단자**, AI = 실행자·검수자·정리자.
- 작업 결과보다 **다음에도 재사용 가능한 시스템**을 우선 남긴다.
